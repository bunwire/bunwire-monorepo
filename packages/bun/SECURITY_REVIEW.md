# Bun package security review — Milestones 16 and 24

This review covers the first stable Bun package contract. It records framework behavior, verification, and the boundary left to application-owned extensions.

| Area | Framework boundary and verification |
| --- | --- |
| Page/HTML output | The default shell escapes script JSON and asset attributes. Page props now reject accessors, sparse/custom arrays, symbols, non-enumerable fields, cycles, and non-JSON values before copying. `tests/bun/milestone-09/pages.test.ts` covers script injection and accessor rejection. Application-supplied `pages.shell` remains trusted rendering code. |
| CSRF | The generated `csrf` middleware requires sessions, checks a session-bound token for unsafe requests, and rejects absent/wrong tokens with 419. `tests/bun/milestone-07/csrf-runtime.test.ts`, `session-process.test.ts`, and the integrated example cover rejection/success. |
| Session fixation/cookies | Session login regenerates the ID and CSRF token; logout invalidates authentication. Session IDs are signed, and cookie defaults are `Secure`, `HttpOnly`, and `SameSite=Lax`. `tests/bun/milestone-07/session.test.ts`, Milestone 8 security tests, and the integrated example cover these paths. The local HTTP example explicitly disables `Secure`. |
| OAuth state | Authorization Code + S256 PKCE stores random state and verifier in the server-side session, checks expiry/provider association, and consumes a matching flow once. `tests/bun/milestone-08/oauth.test.ts` covers missing, mismatched, expired, and replayed state. Provider identity mapping is application-owned. |
| Principal/authorization isolation | Auth contexts are created per HTTP request. Built-in `auth`, `guest`, and `can` middleware resolve against that context; authorization failures use standard 401/403 paths. Milestone 8 runtime/process tests and the integrated example cover login, denial, and logout. |
| Error disclosure | Production unknown exceptions render a generic 500, while explicit development mode may include details. Milestone 3 and 5 HTTP tests verify response behavior. Custom exception handlers are trusted application code. |
| Queued payloads/deserialization | The default serializer accepts lossless JSON tuples only and rejects cycles, accessors, hidden/symbol keys, non-plain instances, unsafe numbers, and malformed payloads. Versioned envelopes and canonical job IDs are checked before invocation; event codecs must reconstruct their exact canonical event class. Milestone 11/12 queue, worker, and codec tests cover these paths. Custom serializers and drivers are trusted extensions. |
| WebSocket upgrade | Global/class middleware runs in the HTTP request scope before upgrade. Only explicitly mapped durable JSON identity crosses into a connection scope; message scopes are children and dispose after each message. Milestone 15 process/identity tests and the integrated example cover denied/authorized upgrades, isolation, and shutdown. |
| Object input/prototype keys | Form Request query/body/route merging retains own special keys without prototype assignment; file, validation-error, and normalized session records use null prototypes. Page props use descriptor validation before any copy. Milestone 6 special-field, Milestone 7 session, and Milestone 9 page tests cover the public input behavior. |
| Signed links and secrets | Signing uses an explicitly configured 32-byte-minimum secret, a canonical method/path/ordered-query payload, and HMAC verification. Reserved and duplicate signature/expiry parameters fail. Request Host and forwarded headers never select an origin. The v2 example signs a protected route and tests path tampering; Milestone 18 covers duplicate and encoded queries. The example's fallback secrets are for local development only. Replacing a signing secret invalidates prior links. |
| Rate-limit identity | The v2 example derives the key from the authenticated principal, never a caller header, and namespaces it by policy. Milestone 20 tests backend atomicity and fail-open/closed behavior; Milestone 24 exercises authenticated signed-route exhaustion. The memory backend is process-local, so distributed enforcement needs an external atomic backend. |
| File and page input | Native `File` presence, declared MIME metadata, and byte limit use the existing Form Request lifecycle. MIME is client-supplied metadata, not byte inspection. Validation errors follow the existing page redirect and one-request flash path; the v2 example tests invalid and accepted multipart requests. Partial and deferred page requests repeat route authentication and authorization in fresh request scopes. |
| Operational disclosure | Health responses reveal only `ok` or `unavailable`, omit readiness check details, and set `no-store`. Maintenance bypass requires an application callback; the example enables it only when an explicit operator environment key is present. Readiness fails during maintenance/shutdown. Milestone 19 and 24 process tests exercise these states. |
| Commands and prompts | Generated inspection commands use the registry and do not start the HTTP host in the command role. Noninteractive prompts fail with a usage result or take only an explicit fallback; Milestone 21 process tests cover both paths. Do not pass secrets as prompt defaults or command-line arguments where process listings may expose them. |
| WebSocket messages | Envelope types are explicit named validators, with malformed opted-in input closing only its connection using code `1007`. Outgoing payloads must survive JSON encoding. Channel joins use frozen post-upgrade identity and a callable application policy; missing policy denies joins. Subscriptions are bounded and cleared on close/shutdown. Milestones 23 and 24 test malformed input, denial, multi-client isolation, and delivery behavior. Native socket APIs remain an application-owned escape hatch. |

Milestone 24 review found an outgoing WebSocket envelope edge case: a payload validator could accept `undefined`, which JSON encoding omits. Encoding now checks that the serialized payload remains present and valid. No page wire version, queue envelope, session persistence format, or generated registry schema changed. Applications remain responsible for their authorization rules, trusted extensions, durable infrastructure, production secrets, and deployment TLS.
